## Session Work Log — 2026-07-03 (MeshCore Protocol Audit)

| Fix | File(s) | Root Cause |
|-----|---------|------------|
| 0x88 (PUSH_CHANNEL_MSG) is LOG_DATA, not a channel message push | `meshcore.py` | meshcore-py v2.3 library: `PacketType.LOG_DATA = 0x88`. ECH was treating it as a formatted channel message with [ch_idx][pubkey×6][plen][ts][body] — every received OTA frame dispatched as garbage to router/bot. Now extracts SNR/RSSI only; channel messages exclusively via polled 0x08/0x11. |
| GET_CONTACTS running every ~2 min | `meshcore.py` | Line in 0x88 handler set `_contacts_refresh_pending=True` for every new-node-from-0x88. With 265+ nodes and active mesh, new senders appeared constantly. Removed — contacts now only refresh on 300s schedule or PUSH_ADVERT. |
| PUSH_MSG_WAITING serial collision during GET_CONTACTS | `meshcore.py` | `PUSH_MSG_WAITING` (0x83) handler sent `CMD_SYNC_NEXT_MESSAGE` immediately without checking `_contacts_in_progress`. Serial bus collision → device returned ERROR → DM dropped. Fixed: set `_msg_poll_pending` flag if in progress; drain immediately after CONTACT_END. |
| poll_interval 15s too slow for bot responses | `/etc/ech/config.yaml` (live server) | Config had `poll_interval: 15` (seconds between CMD_SYNC_NEXT_MESSAGE polls). Patched live to 5s. Reference config already shows 2.0s default. |
| DM receipt logged at DEBUG level | `meshcore.py`, `mesh_bot.py` | DM receipt and bot command handling both logged at DEBUG — invisible in production. Promoted to INFO. Added explicit DM log in `mesh_bot.py handle()` so all incoming DMs are visible. |
| `_contacts_min_interval` too short (120s) | `meshcore.py` | Triggered contacts refreshes could still fire every 2 min. Changed to 600s (10 min). |
